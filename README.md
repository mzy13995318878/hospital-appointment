# 医院门诊号源预约与候补系统

**仓库地址：https://github.com/mzy13995318878/hospital-appointment**

> 数媒程序开发组 10 月考核项目 · FastAPI + SQLite + 原生前端 · 零构建

给三甲医院热门科室做的号源预约演示系统。核心机制一句话就能说清：

**号源有限 → 有余号直接约 → 无余号自动进候补 → 有人退号则队首自动转正。**

难点全在"自动转正"这四个字上：它要求**一个号永远只属于一个人**（不能超卖），
同时要求在有人退号时**立刻**把空号递补给排队的第一位（不能漏号）。
这两件事在单人操作时都很简单，难的是**多人同时操作**时依然成立——
本项目的绝大部分设计与测试，都是围绕这一点展开的。

---

## 1. 快速开始

```bash
# ① 装依赖（Python 3.10 以上即可，本项目实测 3.13.12）
python -m pip install -r requirements.txt

# ② 启动
python -m uvicorn app.main:app --host 0.0.0.0 --port 8000

# ③ 打开
#    首页（号源列表）  http://127.0.0.1:8000/
#    接口文档（可交互） http://127.0.0.1:8000/docs
```

数据库会在启动时**自动创建并灌入演示数据**，不需要手动初始化。

> **演示场合请改用 `scripts/serve.bat`（双击即可）或 `bash scripts/serve.sh`。**
> 这两个脚本里写了三条硬性要求，每一条都对应过一次真实的"演示卡死"事故，
> 手动敲命令很容易漏掉其中某一条。详见脚本内的注释。

想恢复出厂数据：

```bash
python scripts/reset_db.py        # 删库重建，回到标准演示状态
```

跑测试（59 条，约 20 秒）：

```bash
python -m pytest tests/ -q
```

## 2. 打开就能看到的演示数据

系统预置 **20 位医生 / 16 个科室 / 67 条排班 / 1709 个号源**，
外加 811 位用户、746 条预约、6 条候补。
**排班日期全部相对"今天"动态生成**，任何时候重建，数据都落在未来。

其中**排班 1–8 是答辩现场要操作的演示组**，位置与状态固定，不随背景数据变化：

| 排班 | 科室 · 医生 | 日期 | 时段 | 号源 | 状态 | 它负责演示什么 |
|---|---|---|---|---|---|---|
| 1 | 口腔科 李建国 | 明天 | 上午 | 12/12 | **候补中（排队 2 人）** | 退号递补的主战场 |
| 2 | 儿科 张丽华 | 明天 | 上午 | 25/40 | 可约 | 正常预约 |
| 3 | 皮肤科 陈静怡 | 明天 | 下午 | 12/30 | 可约 | 正常预约 |
| 4 | 心内科 王志远 | 后天 | 上午 | 12/12 | **已满（无人排队）** | 与排班 1 对照 |
| 5 | 神经内科 赵敏华 | 后天 | 上午 | 3/20 | 可约 | 正常预约 |
| 6 | 骨科 刘明远 | 后天 | 下午 | 3/25 | 可约 | 正常预约 |
| 7 | 口腔科 李建国 | **今天** | 下午 | 0/20 | **已停诊** | 打开就在第一屏 |
| 8 | 皮肤科 陈静怡 | 明天 | 上午 | 0/30 | 可约 | 与排班 3 同天同科室 |

**排班 1 与排班 4 是刻意做成一对的**：两者的号都是 12/12，唯一差别是有没有人排队。
一个显示"候补中"，另一个显示"已满"——一眼就能看出"有人排队"到底改变了什么。
排班 3 与排班 8 是另一对：同天同科室，用来演示防黄牛规则（一天一科室只能约一个号）。

### 背景排班：59 条，负责"像一家医院"

上面 8 条之外，`sql/seed.sql` 还会按「20 位医生 × 7 天 × 上下午」批量生成约 59 条背景排班，
把科室列表从"样例数据"撑成"一周门诊表"。热门科室（心内科、儿科、骨科、普通外科）
刻意配了两位医生且职称分高低，因为真实医院不会一个科室只有一个医生。

生成规则全部是整数取模，**不用随机数**——种子数据必须可复现，
否则今天重建的库里 3 号是空的、明天重建就满了，
演示时照着文档点下去却发现状态对不上，这种问题根本没法排查。

两个刻意的设计：

- **背景排班从明天开始，不含今天。** 排班一旦开诊就不能再约，
  而种子数据无法预知建库时刻——深夜建库，今天上午的号早开诊了；凌晨建库又能约。
  同一份脚本跑出两种结果，正是"可复现"要避免的。
  这也正好对上真实医院"提前 7 天放号"的规则。
- **演示组与背景组严格分离。** 排班 1–8、预约 1–68、用户 1–11 只做追加、永不回头改。
  因为 `docs/DEMO.md` 的台本和 `scripts/verify_demo.py` 的 17 项自检都是照着这些 id 写的，
  改一次要同步三处，漏一处就会变成"台上演示到一半发现和文档对不上"。

科室多了之后，**演示时请用列表页的科室筛选定位**：选「口腔科」直达排班 1（明天上午那条）。

## 3. 功能清单

### 3.1 核心链路

| 功能 | 实现位置 | 说明 |
|---|---|---|
| 号源列表与三重筛选 | `static/index.html` + `routers/schedules.py` | 科室 / 日期 / 状态任意组合 |
| 医生详情 | `static/doctor.html` | 内嵌排班，与列表页**共用同一个渲染函数** |
| 三要素登录 | `static/login.html` + `routers/auth.py` | 姓名 + 身份证后 4 位 + 手机号，未登记则自动建档 |
| 预约 / 自动转候补 | `services/booking.py::create_booking` | 一个事务内决定给号还是排队 |
| 退号 + 自动递补 | `services/booking.py::cancel_booking` | 退号与递补在**同一个事务**里完成 |
| 我的预约 / 我的候补 | `static/mine.html` | 含"退出排队" |
| 防黄牛三条 | `services/guards.py` | 同时段重复、同天同科室、重复排队 |

### 3.2 加分项（五个全部实现）

原计划"三选二"，最终五个全做。

| # | 加分项 | 参数 | 关键实现 |
|---|---|---|---|
| 1 | 退号冷却期 | 10 分钟 | `guards.assert_not_in_cooldown()`，查 `appointments.cancelled_at` |
| 2 | 转正确认超时 | 15 分钟 | 递补出来的是 `pending`，带 `confirm_deadline`，逾期作废顺延 |
| 3 | 就诊签到 | — | `POST /appointments/{id}/check-in`，过期未签到惰性结算为 `no_show` |
| 4 | 取消时限 | 开诊前 2 小时 | `guards.assert_cancel_window_open()`，时段→开诊时刻映射 |
| 5 | 违规拉黑 | 爽约 2 次 | 自动累计 + 手动管理接口 |

五个里有四个要判断"现在几点"，所以动工之前先统一了两件事：
**`services/policy.py` 存放全部阈值，`services/clock.py` 是全项目唯一的时间出口。**
可注入时钟让测试能把整个系统（**包括 SQL 里的 now**）拨到任意时刻——
否则要验证"15 分钟不确认就顺延"，测试就得真等一刻钟。

## 4. 技术选型：为什么是它，换成别的会怎样

| 层 | 选型 | 理由 | 换成主流方案会怎样 |
|---|---|---|---|
| 后端 | **FastAPI** | 自带交互式接口文档，答辩时可以直接在 `/docs` 上调接口演示，比口头描述有说服力 | 换成 Flask 也能做，但接口文档要自己接 Swagger，`/docs` 这个演示点就没了 |
| 服务器 | **Uvicorn** | FastAPI 官方搭配，一条命令起来 | 换成 gunicorn+worker 会引入多进程，SQLite 单写锁的争论会被"多进程下更严重"放大，反而偏离考点 |
| 数据库 | **SQLite** | 文件即库，天然满足"重启不丢"；**支持部分唯一索引**，防重约束能落到库层面；单写事务串行，正好让并发问题暴露得干净 | 上 MySQL 要改的地方见 `docs/QA.md`，核心逻辑一行不用动，但演示机必须装数据库服务，翻车风险陡增 |
| 前端 | **原生 HTML/CSS/JS** | 零构建，双击即开；代码全在明面上，能逐行解释 | 上 Vue/React 会增加构建步骤，答辩现场"拉代码→装依赖→编译"只要卡一步就开不了场 |
| 测试 | **pytest + httpx + 真进程** | 并发用例起真 uvicorn 进程打真实 HTTP | 只用 TestClient 会把并发串行化掉，测出来的"没超卖"是假象，详见下节 |

### 一个刻意的反直觉选择：路由全部写成同步 `def`

按常识，异步框架里路由应该写 `async def`。**本项目刻意不这么做。**

`async def` 的路由全都在同一个事件循环里串行执行，
同步的 `sqlite3` 调用会堵住整个循环——请求之间根本不重叠，
SQLite 那把写锁**永远不会被竞争**。
那样跑出来的"20 人抢号没有超卖"，证明的不是代码正确，
而是"压根没并发起来"。

写成同步 `def` 后，Starlette 会把它们丢进线程池，
请求才真正重叠，锁才会被真的争抢，测试才有意义。
完整的论证与实测数据见 `docs/CONCURRENCY.md`。

## 5. 代码思路

### 5.1 分层：谁负责什么，边界在哪

```
routers/     只做三件事：解析参数、开事务、把结果包成统一响应
services/    全部业务规则，纯函数式地"做事"，自己不开事务
db.py        连接工厂 + 事务工具 + 结构迁移
```

**事务边界归路由层，service 层只做事不开关。**
代价是每个路由都要写一遍 `with db.transaction(conn)`，
换来的是测试可以在服务层外面随便套事务做断言——
并发测试正是这么跑的：在一个事务里先查后写，验证中间状态。

### 5.2 四条贯穿全项目的规矩

1. **状态只有一处计算。** 剩余号 = `total_slots - booked_count`，号源状态全部派生。
   全项目只有 `services/slot_status.py` 一个地方算它，前端与其它后端模块一律不得自行推导。
2. **并发正确性靠数据库那把锁，不靠"代码写得小心"。** 条件 UPDATE + `BEGIN IMMEDIATE` + 唯一索引，三层各挡一种失效。
3. **对外只有一种错误形状。** `{"ok":false,"error":{"code","message"}}`，连框架自己抛的 422 也被收编成 400 `INVALID_PARAM`——
   前端因此只需要写一套错误解析。
4. **时间与阈值各自只有一处来源。** 数字放 `policy.py`，"现在"取 `clock.py`。

这四条不是风格偏好，每一条都对应过一次真实的事故，
事故经过记在 `PROJECT_STATE.md` 的「关键决策速查」里。

### 5.3 防超卖的三层

```
第一层  条件 UPDATE   UPDATE ... WHERE booked_count < total_slots AND is_closed = 0
                      判断与写入是一个操作，中间没有窗口；
                      停诊条件也写进 WHERE，绕过应用层也占不到停诊的号

第二层  BEGIN IMMEDIATE   写事务一开始就拿锁，而不是写到一半才升级，
                          避免两个事务都读到"还有 1 个号"然后互相覆盖

第三层  部分唯一索引   (schedule_id, seq_no) 与 (schedule_id, user_id) 唯一
                      假设前两层全被绕过，数据库仍然拒绝
```

三层不是冗余备份，**它们挡的是三种不同的失效**：
第一层挡"判断与写入之间的窗口"，第二层挡"读后写被覆盖"，
第三层挡"有人绕过应用层直接改库"。

### 5.4 候补队列是一台延迟求值的规则检查器

这是本项目最重要的一处设计，也是 R3 阶段最关键的发现。

**入队时刻意不校验"同天同科室限 1 号"**——因为那时他确实一个号都没有。
但等到有人退号、轮到他时，情况可能已经变了：
他这中间可能已经约到了同科室的另一个号。

所以**出队时必须重跑三条规则**，不合格者标记 `expired` 顺延给下一位。
这条路径后来被加分项 2「转正确认超时 → 顺延下一位」直接复用，
等于提前把地基打好了。

顺带堵住一个同类漏洞：**队首就是退号者本人时也要顺延。**
否则"先排队 → 再退号 → 递补给自己"能把这个号永久锁在手里——
这正是防黄牛要防的霸号行为。

## 6. 测试：59 条，以及为什么这么分

```bash
python -m pytest tests/ -q          # 59 passed
```

| 文件 | 条数 | 它在证明什么 |
|---|---|---|
| `test_booking.py` | 23 | 预约、候补、递补、顺延、防黄牛、错误形状 |
| `test_concurrency.py` | 4 | **真进程**下抢号不超卖、排队不重名、退号递补不串号 |
| `test_status_consistency.py` | 4 | 状态的两条实现路径结果一致 + **变异测试** |
| `test_schedules.py` | 4 | 过去排班默认隐藏，但一条都没删 |
| `test_extras.py` | 24 | 五个加分项，靠冻结时钟验证超时/冷却/时限/爽约 |

其中两组值得单独说：

**并发组不用 TestClient。** 它把请求逐个构造、逐个走完，请求之间根本不重叠；
换成真进程还不够，还得用 `threading.Barrier` 把 20 个请求的起跑线对齐——
否则线程池是"提交一个立刻跑一个"，很可能第一个都写完提交了、最后一个才刚发出，
它们根本没在抢，只是在排队。

**一致性组配了一套变异测试。** 它证明的不是"代码现在是对的"，
而是"代码要是写错了，这些测试一定会变红"。
四个故意改坏的表达式全部被抓到（漏掉候补分支 2 处、门槛改错 1 处、
判定顺序颠倒 6 处、漏掉停诊分支 12 处）。
**一个从没红过的测试，没人知道它到底在不在测东西。**

## 8. 主动交代的取舍

以下每一条都是**知道代价之后的选择**，不是疏忽。评委问到时，照实说就是加分项。

1. **不做真实鉴权。** 只认 `X-User-Id` 请求头，登录接口是模拟的。
   题目定位是演示系统，真实鉴权（密码哈希、会话、Token 签发）会占掉大量篇幅，
   而它跟"号源会不会超卖"这个考点毫无关系。
   但这带来一个明确后果：**任何人改一下请求头就能冒充他人**，
   因此本系统绝不能用于真实场景。
2. **管理员接口没有鉴权。** `/api/admin/settle` 与拉黑接口任何人都能调。
   它们是为演示"超时结算"和"拉黑"临时开的后门，
   真实系统里必须挡在管理端登录之后。
3. **号源状态不落库，每次现算。** 换来的是"永远不可能与计数不一致"，
   代价是要按状态筛选时，SQL 里得把判定逻辑再写一遍（同一套逻辑两份）。
   三道保险与取舍过程记在 `docs/API.md` 第 6 节。
4. **候补队列的 position 只增不压缩。** 对外名次每次现算。
   压缩需要一条 UPDATE 同时改多行，而 SQLite 逐行检查唯一约束、
   更新顺序不可控，会临时撞键。这是用"展示层多算一次"换"永远不撞键"。
5. **超时判定是惰性的，没有后台定时任务。** 起后台线程的话，
   服务一重启它就没了，而它负责的恰恰是"清理僵尸状态"这类最不该丢的东西。
   惰性结算的代价是：如果一直没人来看，超时记录会一直躺在库里——
   但这不影响任何人的任何决策。
6. **SQLite 单文件。** 并发写靠全局锁串行，这在演示规模下完全够用
   （实测 20 并发抢号最慢 26 ms），但它决定了系统**不能水平扩展**。
   换 MySQL 要改什么，见 `docs/QA.md`。

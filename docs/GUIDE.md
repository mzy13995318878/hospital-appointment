## 1. 先建立一个直觉：这项目到底在干嘛

### 1.1 一句话版本

做一个"限量号码牌"系统：医生一天放 30 个号，30 个人抢完就没了；没抢到的人排队等着，前面有人退号，系统自动把号给队首那个人。

### 1.2 生活类比

把它想成**热门餐厅的现场取号**：

| 现实 | 系统里的对应 |
|---|---|
| 餐厅今天发 30 个号 | `schedules.total_slots = 30` |
| 已发出的号码 | `appointments` 表里的记录 |
| 工作人员手里的号码本 | `schedules.booked_count` |
| 排队等位的人 | `waitlist` 表 |
| 有人走了，喊"下一号" | 候补首位自动转正 |
| 一个人不能拿两个号 | 防黄牛规则 |

关键点是：**号码本是有限的，而且可能有几十个人同时伸手去拿**。整道题的难点全在这一句上。

### 1.3 系统里的三个角色

```
┌──────────────┐         ┌──────────────┐         ┌──────────────┐
│   浏览器      │  请求   │   Python     │   SQL   │   SQLite     │
│  (前端页面)   │ ──────> │  (FastAPI)   │ ──────> │   (账本)     │
│              │ <────── │              │ <────── │              │
└──────────────┘  响应   └──────────────┘  数据   └──────────────┘
   只负责显示          负责全部业务逻辑          只负责存
```

**记住一条铁律**：前端（浏览器）里的数据**一个字都不能信**，所有判断必须在后端做。

原因很实在：浏览器在你自己的电脑上，用户按 F12 就能改任何数据。如果"还能不能约"这个判断放在前端，用户改一下就能无限刷号。这不是假设，这是必然会被做的事。

## 2. 从 C 语言的视角看这个项目

你学过 C 语言课程设计，这个项目其实没那么陌生。做一个对照表：

| C 语言课设 | 这个 Web 项目 |
|---|---|
| `main()` 主函数 | `app/main.py`，但它是**长期运行**的，不会被调用一次就结束 |
| 你自己写的函数 | HTTP 接口（路由），但需要**别人远程调用** |
| `struct` 定义的数据结构 | 数据库表（`CREATE TABLE`） |
| `struct student stu[100]` | 表里的一行行记录 |
| 文件 `fopen/fwrite` | SQLite，但**它帮你保证不出错** |
| `scanf()` 等用户输入 | 浏览器发来的 HTTP 请求 |
| `printf()` 输出结果 | 返回 JSON 数据，由前端渲染成页面 |
| 全局变量 | 数据库里的记录 |

### 2.1 一个根本性的不同

**C 程序：一次只服务一个人。**
你运行 `./a.out`，输入、输出、结束。整个过程只有你一个人在用。

**Web 程序：同时服务所有人，而且它们会互相干扰。**

```
用户甲的点击 ──┐
用户乙的点击 ──┼──> 同一个进程 ──> 同一份数据
用户丙的点击 ──┘
```

这就是第 5 节要解决的并发问题。C 课设里你从没考虑过这件事（因为不需要），但这里是**核心考点**。

### 2.2 HTTP 到底是什么

把它理解成**函数调用，只不过函数运行在另一台机器上**。

C 里你写：

```c
int result = add(3, 5);
```

Web 里前端"调用"后端的函数，靠的是 URL：

```
GET  /api/schedules?department=口腔科     →  相当于  schedules("口腔科")
POST /api/appointments  {"schedule_id":1} →  相当于  create_appointment(1)
DELETE /api/appointments/12              →  相当于  cancel_appointment(12)
```

| C 概念 | HTTP 对应 |
|---|---|
| 函数名 | URL 路径 `/api/appointments` |
| 函数参数 | URL 后面的 `?a=1&b=2`，或请求体里的 JSON |
| 返回值 | HTTP 响应体（通常是 JSON） |
| 函数的几种调用约定 | `GET`（查）/ `POST`（增）/ `PUT`（改）/ `DELETE`（删） |

**JSON 是什么**：就是一种把数据写成文本的格式，等价于 C 的 struct 序列化：

```json
{ "doctor_name": "李建国", "total_slots": 3, "remaining": 0 }
```

### 2.3 前端和后端怎么"分开"

- **后端（Python）**：不看长相，只处理数据和规则。你让它预约，它返回 `{ "type": "waitlisted", "position": 2 }`。
- **前端（HTML/CSS/JS）**：不懂规则，只负责把后端返回的数据画成好看的页面，再把用户的点击变成请求发出去。

两边约定好"你给我什么、我给你什么"，这份约定就是 `docs/API.md`。

**为什么这个约定很值钱**：因为它让前后端可以分头开发。R2/R3 只写后端，R4 只写前端，只要都照着 `API.md` 写，拼起来就能跑。

## 3. 跑一趟完整流程：点一下"预约"会发生什么

这是理解整个系统最重要的一张图。跟着走一遍：

```
① 用户在浏览器点「预约」按钮
        │
        ▼
② 前端 JS 取出 localStorage 里的 user_id
   发出：POST /api/appointments
        请求头带 X-User-Id: 3
        请求体带 {"schedule_id": 1}
        │
        ▼
③ FastAPI 的路由函数收到请求
   app/routers/appointments.py  →  create_appointment()
        │
        ▼
④ 从请求头解析出当前用户是谁
   app/deps.py  →  current_user()
        │
        ▼
⑤ 开启数据库事务：BEGIN IMMEDIATE
   （从这一刻起，别人抢号要排队等我）
        │
        ▼
⑥ 校验三条防黄牛规则
   app/services/guards.py  →  assert_bookable()
   不通过 → 抛异常 → 回滚 → 返回 409
        │
        ▼
⑦ 尝试占号（关键一步！）
   UPDATE schedules SET booked_count = booked_count + 1
    WHERE id = 1 AND booked_count < total_slots
        │
        ├── 影响 1 行 → 抢到了！
        │      └─> 算最小可用序号 → 插入 appointments 记录
        │          └─> 返回 {"type": "booked", "seq_no": 1}
        │
        └── 影响 0 行 → 号没了
               └─> 插入 waitlist 记录，算出排队位置
                   └─> 返回 {"type": "waitlisted", "position": 2}
        │
        ▼
⑧ COMMIT 提交事务，释放锁
        │
        ▼
⑨ 返回 JSON 给前端
        │
        ▼
⑩ 前端根据 type 显示不同提示：
   "预约成功，你是 1 号"  或  "已排队，你是第 2 位"
```

**注意第 ⑦ 步**：这里是整个系统唯一决定"你有没有抢到号"的地方。它不是一个 `if` 判断，而是一条**带条件的 UPDATE 语句**。原因见第 5 节。

## 4. 数据库五张表，用人话解释

### 4.1 `users` —— 谁在挂号

存"人"。题目说不用真的对接公安系统，所以我们只记三样：姓名、身份证后四位、手机号。

**为什么这三样组合起来就是唯一的人**：假设两个人同名同姓"张伟"，但身份证后四位和手机号都一样的概率为零。所以：

```sql
UNIQUE(name, id_card_last4, phone)
```

登录时：三样都匹配 → 老用户，直接放行；匹配不上 → 新用户，自动注册。

### 4.2 `doctors` —— 医生是谁

存医生的固定信息：姓名、职称、科室、简介、擅长方向。

**为什么要单独一张表，不直接写进排班里**：因为同一个医生会有很多天的排班。如果每次排班都把"李建国，主任医师，口腔科"抄一遍，改职称的时候要改十几行，还容易漏。这叫**数据冗余**。

### 4.3 `schedules` —— 哪天哪个时段放多少号

一行 = 一个医生一天一个时段的号源池：

| 字段 | 含义 |
|---|---|
| `doctor_id` | 哪个医生 |
| `work_date` | 哪天 |
| `period` | 上午 / 下午 / 晚上 |
| `total_slots` | 放多少个号（比如 30） |
| `booked_count` | **已经发出去多少个**（当前 27） |
| `is_closed` | 医生停诊了吗 |

**剩余号 = `total_slots - booked_count`**，永远现场算，不存。理由见决策 1。

### 4.4 `appointments` —— 谁拿到了哪个号

一行 = 一个有效的预约：

| 字段 | 含义 |
|---|---|
| `user_id` | 谁 |
| `schedule_id` | 哪场 |
| `seq_no` | **就诊序号**（1 号、2 号……） |
| `status` | `booked` 待就诊 / `cancelled` 已退 / `completed` 已看完 / `no_show` 爽约 |
| `source` | `direct` 直接约到的 / `promoted` 候补转正的 |

### 4.5 `waitlist` —— 谁在排队

一行 = 一个排队的人：

| 字段 | 含义 |
|---|---|
| `position` | 排队第几位 |
| `status` | `waiting` 排队中 / `promoted` 已转正 / `cancelled` 放弃了 |
| `joined_at` | 什么时候开始排的 |

### 4.6 一个反直觉的点：为什么分开两张表

你可能会想：预约和候补不都是"想要这个号"吗，合成一张表加个"是不是候补"的标记不行吗？

**不行，而且分开会让代码简单得多。** 因为两者的字段和行为差太多了：

| | 正式预约 | 候补 |
|---|---|---|
| 有就诊序号吗 | 有 | 没有 |
| 占用号源吗 | 占 | 不占 |
| 能取消吗 | 能（还要触发递补） | 能（不影响别人） |
| 冲突规则 | 同时段只能一个 | 同时段只能一个 |

合成一张表的话，你会到处写 `if is_waitlist: ... else: ...`，而且唯一索引（防止一人占俩号）会变得非常难写。分开之后，每张表各自的约束清清楚楚。

## 5. 事务与并发：这道题真正考的东西

**这一节是整份文档最重要的部分。吃透它，答辩就稳了一半。**

### 5.1 问题：两个人同时抢最后一个号

假设某排班总共 3 个号，已经发出去 2 个。此时用户甲和用户乙**同时**点下预约按钮。

正确的结果应该是：**一个人成功，另一个人进候补。**

### 5.2 天真写法会怎么错

如果按"先查再改"的思路写（这是初学者的本能，也是你写 C 课设的思路）：

```python
# 错误示范！
row = db.query("SELECT booked_count, total_slots FROM schedules WHERE id=1")
if row.booked_count < row.total_slots:        # 判断：还有号
    db.execute("INSERT INTO appointments ...")  # 插入预约
    db.execute("UPDATE schedules SET booked_count=%s WHERE id=1" % (row.booked_count + 1))
```

看起来毫无问题。但两个请求交错执行时会这样：

```
时刻  用户甲                              用户乙
─────────────────────────────────────────────────────────
 1    查 booked_count → 2
 2                                       查 booked_count → 2
 3    判断 2 < 3 ✓ 通过
 4                                       判断 2 < 3 ✓ 通过
 5    插入预约记录
 6                                       插入预约记录      ← 两个人都要了！
 7    写 booked_count = 3
 8                                       写 booked_count = 3  ← 值还是 3

结果：booked_count = 3，但实际有 4 条有效预约。
      4 个人来看病，医生只准备看 3 个。
```

这就是**超卖**。售票系统、秒杀系统的经典 bug，原理一模一样。

**根因**：第 3 步的"判断"和第 7 步的"写入"之间有一段时间差，这段时间里数据被别人改了。这叫 **check-then-act（先检查后执行）竞态**。

### 5.3 正确做法一：让数据库替你做判断

核心思路：**不要在 Python 里判断，把判断条件写进 UPDATE 语句，让数据库一次搞定**。

```sql
UPDATE schedules
   SET booked_count = booked_count + 1
 WHERE id = 1
   AND booked_count < total_slots;   -- ← 条件写在这里
```

然后检查这条语句**影响了多少行**：

- 影响 **1 行** → 说明条件成立、更新成功 → 我抢到了
- 影响 **0 行** → 说明在我执行前，别人已经把它加到 3 了 → 号没了，去排队

```
时刻  用户甲                                用户乙
─────────────────────────────────────────────────────────
 1    UPDATE ... WHERE booked_count < 3
      → 影响 1 行，成功！
 2                                         UPDATE ... WHERE booked_count < 3
                                           → 此时 booked_count 已是 3
                                           → 影响 0 行，失败
 3    插入预约记录，拿到 3 号
 4                                         插入候补记录，排第 1 位
```

**为什么这样就对了**：数据库的单条 UPDATE 是**原子操作**——它内部"检查条件"和"修改值"这两步之间不可能被插队。这是数据库引擎保证的，不需要你操心。

用 C 类比：相当于把

```c
if (count < total) { count = count + 1; }
```

换成了一条**不会被打断的** CPU 指令。

### 5.4 正确做法二：事务（一次做多件事要么全成要么全败）

上一节解决了"计数"的问题。但一次预约要做**好几件事**：

1. 检查防黄牛规则
2. 更新 `booked_count`
3. 算出就诊序号
4. 插入 `appointments` 记录

如果第 3 步算不出来（比如序号全被占了），前两步已经改了数据库，怎么办？

**事务**就是解决这个的。它的承诺非常简单：

> 事务里的所有操作，**要么全部成功，要么全部像没发生过一样**。

```python
conn.execute("BEGIN IMMEDIATE")   # 事务开始，同时立刻拿到写锁
try:
    guards.assert_bookable(...)       # 规则校验
    cur = conn.execute(UPDATE ...)    # 条件更新
    if cur.rowcount == 0:
        ...入候补...
    else:
        ...建预约...
    conn.execute("COMMIT")            # 全部成功，落盘
except Exception:
    conn.execute("ROLLBACK")          # 任何一步出错，全部撤销
    raise
```

### 5.5 为什么是 `BEGIN IMMEDIATE` 而不是普通的 `BEGIN`

SQLite 有三种事务开头，区别很大：

| 语句 | 拿锁时机 | 问题 |
|---|---|---|
| `BEGIN`（默认 deferred） | 第一次真正读写时才拿锁 | 两个事务都先读、后想写 → 都想升级成写锁 → **死锁报错** |
| `BEGIN IMMEDIATE` | **一开始就拿写锁** | 后来的事务直接排队等，不会死锁 |

用 `BEGIN IMMEDIATE` 相当于：进门前先把钥匙攥手里，而不是走到柜子前才发现钥匙被人拿走了。

另外 SQLite 同一时刻**只允许一个写事务**，所以我们的预约逻辑天然是串行的——这也是为什么"抢最后一号"必然只有一个赢家。

### 5.6 正确做法三：唯一索引兜底

即使上面的逻辑全写对了，还要再加一道保险：**让数据库禁止非法数据存在**。

```sql
-- 同一个号源，不可能出现两条有效预约
CREATE UNIQUE INDEX ux_appt_slot
    ON appointments(schedule_id, seq_no)
 WHERE status IN ('booked','completed','no_show');

-- 同一个人在同一场排班，不可能有两条有效预约
CREATE UNIQUE INDEX ux_appt_user_slot
    ON appointments(user_id, schedule_id)
 WHERE status IN ('booked','completed','no_show');
```

这样哪怕 Python 代码有 bug（或者将来被人改坏），数据库也会拒绝插入，报错而不是产生脏数据。

**注意 `WHERE` 子句**，这是 SQLite 的**部分索引**（partial index）：

- 只有 `status` 是"有效"的行才进索引、才被约束
- 已 `cancelled` 的历史记录不受影响 → 所以一个人可以退号后再重新约

如果去掉 `WHERE`，索引会连取消记录一起约束，那用户退号后就永远不能再约了——这个坑非常隐蔽。

### 5.7 三层防护总结

答辩时可以这样讲，显得很有层次：

| 层 | 做的事 | 解决什么 |
|---|---|---|
| **第 1 层：数据库原子性** | 条件 `UPDATE ... WHERE booked_count < total_slots` | 防止超卖 |
| **第 2 层：事务** | `BEGIN IMMEDIATE` 包裹全部操作 | 防止改到一半的状态 |
| **第 3 层：唯一索引** | 部分唯一索引约束 | 即使代码有 bug，脏数据也进不来 |

**为什么要三层，一层不够吗**：第 1 层只能保证"计数不超"，保证不了"同一个人不会约两次"（那是另一条规则）；第 2 层保证完整性但不保证业务正确；第 3 层是兜底，只在出 bug 时体现价值。**三层覆盖的是不同的失效场景**，不是重复劳动。

### 5.8 怎么证明它真的有效

光说没用，R5 会写一个并发测试：

```python
# 起一个真实服务，用 20 个线程同时去抢只剩 1 个号的排班
# 断言：成功的请求数恰好等于 1，其余 19 个全部进候补
```

**测试必须打真实的 uvicorn 服务**，不能用 FastAPI 的 `TestClient`——因为 TestClient 是单线程模拟的，根本并发不起来，测了等于没测。这一点 R5 要特别注意。

## 6. 六个关键决策：人话版

技术版在 `DATA_MODEL.md` 第 3 节，这里讲"为什么"。

### 决策 1：剩余号不存数据库

**做法**：`剩余 = 总数 - 已约数`，每次现算。

**为什么**：一旦你存两个字段，就得保证它们永远同步。只要有一处代码忘了同时改，就会出现"页面显示还剩 3 个，实际点进去说没号了"。派生值没有不一致的可能，因为压根不存在"两个值"。

**答辩话术**："我用空间换一致性——多算一次减法的成本几乎为零，换来的是数据永远自洽。"

### 决策 2：号源状态也不存，只有"停诊"存

四种状态里，"可约 / 已满 / 候补中"全是瞬时事实，靠数据现推：

| 显示 | 判断条件 |
|---|---|
| 已停诊 | `is_closed = 1` |
| 可约 | 未停诊 且 已约 < 总数 |
| 候补中 | 满了 且 有人在排队 |
| 已满 | 满了 且 没人排队 |

**为什么**：「已满」和「候补中」的区别只是"有没有人排队"。如果存成字段，每次有人入队、离队都要记得同步改它——多一处会忘的地方。

### 决策 3：就诊序号取"最小空号"，不用 MAX+1

**这是个真实会炸的坑。** 假设总共 3 个号：

```
1号 ✓ 2号 ✓ 3号 ✓      ← 满了
↓ 1 号的人退号
1号 ✗ 2号 ✓ 3号 ✓      ← 空出 1 号
↓ 新人预约
MAX(seq_no) + 1 = 3 + 1 = 4   ← 超出总数上限了！
```

**正确做法**：在 1 到总数之间，找最小的、没人占用的号。上面这个例子里新人拿到 1 号。

```python
used = {r["seq_no"] for r in ...}          # 当前被占用的序号集合
seq  = next(n for n in range(1, total+1) if n not in used)
```

**答辩话术**："序号的语义是'第几个就诊'，它必须在 1 到总数这个范围内，是个有界集合，不能用自增数列来生成。"

### 决策 4：取消是"软删除"

**做法**：`UPDATE appointments SET status='cancelled'`，记录留着，不 DELETE。

**为什么**：
1. 加分项（爽约统计、违规拉黑、退号冷却期）全都要看历史——删了就没了；
2. 万一出纠纷，得能查"这人这个月退了几次号"；
3. 配合部分唯一索引，历史记录不干扰"一人一号"的约束。

**答辩话术**："取消不是'这件事没发生过'，而是'这件事被撤销了'——后者需要留下证据。"

### 决策 5：候补转正继承退号者的序号

**做法**：1 号退号，候补第一位的那个人拿到 1 号，而不是被排到队尾。

**为什么**：因为那个号本来就空出来了，语义上就该由递补者填补。而且这样序号始终连续，不会出现"3 号、7 号、12 号"这种带洞的序列——对分诊台护士来说，连续的序号才好叫号。

同时 `source = 'promoted'` 留下痕迹，前端可以标注"候补转正"。

### 决策 6：防黄牛三条规则分两层实现

| 规则 | 在哪实现 | 怎么做 |
|---|---|---|
| 同时段不可重复预约 | 数据库 + 代码 | 唯一索引兜底 + 事务内先查 |
| 同天同科室最多 1 个号 | **只能靠代码** | 跨三张表查询 |
| 数据持久化 | 存储层 | SQLite 文件落盘 |

**第二条为什么数据库做不到**：唯一索引只能约束"同一张表的某几列"，而"同一天同一科室"需要把 `appointments`、`schedules`、`doctors` 三张表连起来查——这个条件无法表达成索引。所以必须在事务里手写 SQL 查。

**一个需要主动说明的取舍**：这条限制**只算正式预约，候补不计入**。理由是候补还没占到任何号源，如果也限制，患者想给同科室两个医生各排一个候补都不行，反而降低了抢到号的概率，与便民目标相悖。这个取舍要在 README 里主动写出来，别等评委问。

### 7.1 路由层和服务层为什么要分开

这是这个项目最值得学的工程习惯：

| | 路由层（routers/） | 服务层（services/） |
|---|---|---|
| 关心 | HTTP：请求头、状态码、JSON | 业务：规则、事务、SQL |
| 不关心 | 具体怎么查数据库 | 数据是怎么传进来的 |

**分开的好处**：

1. **可测试**：R5 写测试时可以直接调服务层函数，不用起 HTTP 服务；
2. **可复用**：将来加一个"微信小程序端"，服务层一行不用改；
3. **好读**：看路由层知道有哪些接口，看服务层知道有什么规则。

如果你把 SQL 和 HTTP 混在一个函数里，将来改任何一个都要小心翼翼。

### 7.2 事务边界归谁管

**约定：服务层自己不开事务也不提交，事务由路由层控制。**

```python
# routers/appointments.py
conn.execute("BEGIN IMMEDIATE")
try:
    result = booking.create_booking(conn, user_id, schedule_id)   # 服务层只管业务逻辑
    conn.execute("COMMIT")
except BookingError:
    conn.execute("ROLLBACK")
    raise
```

**为什么这么定**：因为一次预约可能要调多个服务函数（校验、占号、记录），让服务层各自提交的话，就没法保证"要么全成要么全败"了。事务边界放在最外层，整个请求才算一个完整单元。

## 8. 答辩高频问题与回答思路

### Q1：为什么用 SQLite 不用 MySQL？

**别只说"因为简单"**，要说清楚取舍：

> 三个原因。第一，零配置——评委拿到代码不用装数据库服务就能跑，演示不翻车。第二，SQLite 单个写事务串行，反而天然帮我保证了"抢最后一号只有一个赢家"。第三，题目要求的"重启不丢"，文件落盘就是最直接的证明。
>
> 代价我也清楚：SQLite 不支持多机部署、写并发能力弱。如果换成真实医院的系统，我会换 MySQL，并且把现在的条件 UPDATE 保留——那套逻辑是通用的，只是连接层和锁粒度要调整。

**加分点**：主动说出代价，并说明迁移路径。

### Q2：并发到底怎么保证的？

见第 5 节三层防护：**条件 UPDATE 防超卖 → 事务保证完整性 → 唯一索引兜底**。最后补一句"我用 20 线程并发测试验证过，成功数恰好等于剩余号数"。

### Q3：如果数据量上来了怎么办？

> 三个瓶颈依次出现：SQLite 写锁 → 单机 CPU → 候补队列计算。
> 应对分别是：换 MySQL 并用 `SELECT ... FOR UPDATE` 行锁；服务层横向扩展，用 Redis 做号源缓存；候补队列改用 Redis 的有序集合（ZSET）。**但核心的"条件更新"思路不变**——它从数据库原语变成了分布式锁下的同一套逻辑。

### Q4：为什么前端不用 Vue/React？

> 这个项目页面只有四个，交互以"点击→刷新列表"为主，引入框架带来的构建配置和心智负担大于收益。而且原生实现让我必须手写每个 DOM 操作，反而逼我把后端返回的每个字段都用明白——答辩时我能解释清每一行前端代码。
>
> 如果页面增加到十几个、或者需要复杂的表单联动，我会换 Vue3。

### Q5：身份校验为什么不做真的？

> 题目明确要求"模拟即可，不要求对接公安身份核验或短信网关"。我保留了 `users` 表的完整身份字段和唯一约束，真实接入时只需要把登录接口里"自动注册"那一步换成调用公安接口，其余代码不用动。

**加分点**：说明"接口已经预留好了，换一行就行"。

### Q6：取消预约会在什么时候出问题？

这是开放题，考察你有没有想过边界。可以答：

> 三个我考虑过的边界。第一，重复取消——用状态判断挡掉。第二，取消时正好有并发预约在抢这个号——靠事务串行化解决，要么我先退完他再抢，要么他先抢完我再退，不会出现"号退了但没递补上"的中间态。第三，临近开诊还退号——这是我做加分项时加的取消时限规则。

### Q7：你怎么测试的？

> 分两层。规则层用 pytest 覆盖三条防黄牛约束和序号生成；并发层起一个真实的 uvicorn 服务，用 20 个线程同时抢只剩 1 个号的排班，断言成功数恰好为 1。测试脚本在 `tests/` 下，可以复现。

### Q8：这个项目最难的部分是哪块？

**如实说：退号递补。**

> 一次取消要连续做五件事：释放号源、找到候补队首、把队首转正、继承序号、更新计数。这五件必须在一个事务里，任何一步失败都要整体回滚。而且这期间可能有另一个人正在抢同一个号。我在 `booking.py` 里把它们全部包在 `BEGIN IMMEDIATE` 里，靠 SQLite 的写串行化保证不会交错。

## 9. 技术名词速查

| 名词 | 一句话解释 |
|---|---|
| **HTTP** | 浏览器和服务器说话的规矩 |
| **GET / POST / DELETE** | 查 / 增 / 删，对应不同的操作意图 |
| **JSON** | 把数据写成文本的格式，`{"key": value}` |
| **API / 接口** | 后端开放出来给前端调用的函数（用 URL 表示） |
| **路由** | URL 路径到 Python 函数的对应关系 |
| **SQL** | 跟数据库说话的语言 |
| **表 / 行 / 列** | 类比 Excel 的工作表 / 一行 / 一列 |
| **主键 (PK)** | 一行数据的唯一身份证号 |
| **外键 (FK)** | 指向另一张表某一行的"引用" |
| **索引** | 给表加的目录，让查询变快 |
| **唯一索引** | 加了约束的目录：重复的插不进去 |
| **事务** | 一组操作，要么全成功要么全撤销 |
| **COMMIT / ROLLBACK** | 提交（落盘）/ 回滚（撤销） |
| **并发** | 多个人同时操作同一份数据 |
| **竞态** | 因为执行顺序不确定导致的 bug |
| **原子操作** | 不可被打断的操作，执行时别人插不进来 |
| **锁** | 保证同一时刻只有一个人能改数据 |
| **死锁** | 两个人互相等对方放手，谁也进行不下去 |
| **幂等** | 同样的操作做多次，结果一样（比如重复取消不会报错） |
| **uvicorn** | 跑 Python Web 程序的服务器软件 |
| **虚拟环境 venv** | 给每个项目单独的 Python 包目录，互不污染 |
| **端口** | 一台电脑上区分不同服务的编号，8000 就是我们的 |
| **F12 开发者工具** | 浏览器里能看请求、改页面的工具——所以它不可信 |

## 10. 最后：这份项目真正的价值在哪

做完后你真正学会的东西，按重要性排：

1. **并发与事务**——这是后端工程师的分水岭，大部分自学项目根本不会碰到；
2. **契约先行**——先写 `API.md` 和 `DATA_MODEL.md` 再写代码，这是团队开发的真实做法；
3. **分层**——路由层和服务层分开，是代码可维护的基础；
4. **取舍意识**——每个决策都要能说出"为什么这么选、换了会怎样"，这比代码本身值钱。

第 4 条最重要。评委问你问题，本质上不是想知道你怎么写的，而是想知道**你知不知道还有别的写法，以及为什么没选它**。

# 并发验证报告

> 本文回答一个问题：**两个人同时抢最后一个号，会不会都成功？**
>
> 答案是不会。但"不会"这两个字本身一文不值 ——
> 本文记录的是**怎么证明它**，以及证明过程中抓到的那个真 bug。
> 所有数字都是 `pytest tests/test_concurrency.py -s` 的真实输出，不是"应该没问题"。

---

## 1. 测试环境：为什么不能用 TestClient

FastAPI 官方推荐的 `TestClient` 在这个场景下**会给假答案**。

| 问题 | 后果 |
|---|---|
| 请求逐个构造、逐个走完，请求之间根本不重叠 | **并发被串行化掉了**，测出来的"并发安全"是假象 |
| 不经过网络层 | socket 排队、连接复用这些真实开销观察不到 |
| 共用当前进程的内存 | 能用依赖覆盖把数据库指到临时文件；但也因此跨不了进程边界 |

于是改跑**真的 uvicorn 独立进程**（`tests/conftest.py` 的 `LiveServer`）：

```python
proc = subprocess.Popen(
    [sys.executable, "-m", "uvicorn", "app.main:app", "--port", str(port), ...],
    env={**os.environ, db.DB_PATH_ENV: str(path)},   # 用环境变量指到临时库
    stdout=subprocess.DEVNULL, stderr=subprocess.DEVNULL,
)
```

跨进程之后，FastAPI 的依赖覆盖就失效了（它只在当前进程内有效），
所以改用 `CLINIC_DB` 环境变量把服务指到临时库 —— 这也是 `db.resolve_db_path()`
存在的理由。**并发测试绝不能去写演示库**，否则演示时会出现一堆"占位 37 号"的脏数据。

端口不写死：`_free_port()` 向系统要一个空闲端口。写死 8001 撞车时报的是
`Address already in use`，看起来像代码有 bug，实际只是端口被占。

就绪探针用 `/api/departments` 而不是专门的 `/api/health`：
本项目没有健康检查接口，而临时加一个要先改契约，不值得。
用真实业务接口反而**更好** —— 它证明的不只是"端口通了"，
而是路由已注册、静态目录已挂载、数据库连接已可用，整个 app 真正装配完成。
一个只返回 `{"status":"ok"}` 的假探针证明不了这些，服务还没准备好它就会先返回 200。

## 2. 换进程还不够：并发得真的发生

起了真进程，还有两个前提，缺一个就白测。

### 前提一：路由必须是同步 `def`

Starlette 会把同步路由函数**丢进线程池**执行，请求之间才会真正重叠。

若当初写成 `async def`，它们会挤在同一个事件循环里串行执行，
SQLite 那把锁永远不会被竞争 —— 那样测出来的"没有超卖"毫无说服力。

> 这条是**为了可测性而做的架构选择**，不是随手写的。
> 换成 `async def` 也能让某个报错消失（见第 4 节），
> 但代价是所有请求被串行化，等于为了让一个检查通过而废掉并发能力。

### 前提二：请求得真的同时到达

线程池是"提交一个、立刻开跑一个"，20 个请求会前后错开 ——
很可能第一个已经写完提交了，最后一个才刚发出，于是它们根本没在抢，只是排队。
**那样的测试测不出超卖，因为它制造的场景本身就没有任何竞争。**

于是用 `threading.Barrier` 对齐起跑线：

```python
barrier = threading.Barrier(n)
def _one(index, task):
    barrier.wait(timeout=30)      # 到齐之前一个都不许先跑
    results[index] = self.request(*task)
```

Barrier 坏了（有同伴超时没赶上）就降级为"不齐也要测"，
总比整个用例挂掉强 —— 那只会让人生出"这测试不稳定"的错觉。

## 3. 防超卖的三层，各挡一种失效

| 层 | 做法 | 挡住什么 |
|---|---|---|
| 应用层 | 条件 UPDATE：把"还有号"写进 `WHERE` | 判断与写入之间被人插队 |
| 事务层 | `BEGIN IMMEDIATE` | 两个事务互相等对方的读锁（死锁） |
| 存储层 | 部分唯一索引 + `CHECK (booked_count <= total_slots)` | 应用层被绕过时（直接写库、代码改错、未来新增入口） |

**关键在第三层**：前两层都在应用层，它们防的是"我们自己的代码写对了"。
第三层防的是"代码写错了"或"有人绕过了代码"。
两者防的是不同环节，不是重复劳动。

```sql
UPDATE schedules SET booked_count = booked_count + 1
 WHERE id = ? AND booked_count < total_slots AND is_closed = 0
```

判断与写入由数据库合成一个**不可打断**的操作。
末尾那个 `rowcount == 1` 的检查是必须的：
条件不满足时 SQLite 不会报错，只是安静地什么都不做。

顺带把 `is_closed = 0` 也写进 WHERE —— 即使应用层校验被绕过，
停诊的排班也占不到号（纵深防御）。

## 4. 这一轮抓到的真 bug：`check_same_thread`

**现象**：并发下每个请求都 500。

```
sqlite3.ProgrammingError: SQLite objects created in a thread
can only be used in that same thread.
```

**根因**：FastAPI 处理 `yield` 型依赖时，会把这个生成器
**扔进一个专门的线程**驱动（`contextmanager_in_threadpool`），
而同步路由函数在**另一个线程池线程**执行 ——
于是"创建连接的线程"与"使用连接的线程"必然不是同一个。

**修法**：`connect()` 加 `check_same_thread=False`。

关掉的是**一条与用法不匹配的保守规则**，不是关掉保护本身。
我们的模型是**一个请求一个连接**：生成器一旦 yield 就停在原地等，
直到请求结束才被唤醒去 close，所以任意时刻真正在碰这个连接的只有一个线程 ——
只是它不是创建者。

**为什么不去改路由**：把路由改成 `async def` 也能绕开（请求就不进线程池了），
但代价是所有请求被串行化 —— 同步的 sqlite3 调用会堵住事件循环，
一个请求在写库时其他请求连进都进不来。本末倒置。

**为什么 23 条旧测试从没发现它**：TestClient 串行处理请求，
anyio 的线程池会**复用同一个 worker 线程**，
创建者和使用者碰巧同线程，问题被完美掩盖。
只有并发起来、请求落到不同线程时才暴露。

> 这是"必须用真 uvicorn 做并发测试"最有力的一条证据：
> 它证明的不是"并发下我们是对的"，而是**"不并发测，根本发现不了错"**。

### 四个用例各自在证明什么

| 用例 | 为什么需要它 |
|---|---|
| 20 人抢 15 个号 | 基本盘：不超卖、不出空洞、记账与实占一致 |
| 10 人抢**最后 1 个**号，连抢 3 轮 | **竞争窗口越窄，有 bug 才越容易暴露**。剩 15 个号时即便代码有竞态，也可能因为运气好而看不出问题；只剩 1 个时，任何疏漏都会立刻显现。连抢 3 轮是因为并发 bug 往往是概率性的，只跑一轮通过说明不了什么 |
| 12 人同时排队 | 名次互不重复，且"对外名次"与"库内排序键"是两套东西仍能一一对应（见 `rank_in_waitlist` 的注释） |
| 3 人同时退号 → 同时递补 | 最复杂的一条：退号与递补必须原子，且三个递补者拿到的是三个**不同**的号 |

最后一个用例尤其关键：递补要跑 `_min_free_seq()` 重新算最小空号，
若这里出现竞态，两个人会拿到同一个就诊序号 ——
那在系统里是**致命**的错误（医生叫到 3 号，站起来两个人）。

## 6. R5 引入 `pending` 之后的并发考量

加分项「转正确认超时」把递补的结果从 `booked` 改成了 `pending`。
这对并发提出了新问题，逐一说明：

**一、`pending` 也要占号，所以它必须进三层防护。**
它进了 `ACTIVE_STATUS_CLAUSE`（最小空号算法会排掉它）、
进了两个部分唯一索引的 WHERE（别人插不进同一序号、同一人插不进第二条有效预约）、
也参与 `booked_count` 加减。少任何一处，这 15 分钟里就会出现超卖。

**二、pending 超时后的顺延，本身是一次并发写。**
`_settle_expired_pending()` 作废一条 pending 之后会立刻调 `_promote_next()`
给下一位 —— 这段逻辑与退号递补**共用同一段代码**，也就共用同一套锁保护。
刻意不另写一套"超时专用"的递补逻辑：两套递补路径，等于两套要各自维护的竞态防护。

**三、惰性结算的触发点可能在并发下重叠。**
两个人同时打开"我的预约"，会同时触发 `settle_all()`。
这不会出问题，靠的是两点：
`BEGIN IMMEDIATE` 让两个结算请求排队执行（后来者进屋就攥着钥匙），
而结算本身是**幂等**的（见 `test_settle_is_idempotent`）——
第二个人扫到的是已经被清理过的状态，什么也不会做。

**四、结算与确认必须分开提交。**
`POST /api/appointments/{id}/confirm` 会先结算再抛"已超时"。
两者若在同一个事务里，抛异常会把结算一并回滚，
于是号又变回 `pending` —— 用户刷新一下发现自己还能确认，
而那个号已经顺延给别人了。这条不是并发 bug，
但它在并发下会造成两个人同时持有一个号的**数据事故**，
所以在这里一并记下（详见 `PROJECT_STATE.md` 决策 25）。

## 7. 怎么跑

```bash
# 只跑并发用例（要 -s 才能看到上面的实测输出）
pytest tests/test_concurrency.py -s

# 全量（59 条）
pytest tests/ -q
```

并发用例会各自起一个独立的 uvicorn 进程与独立端口，跑完自动停掉。
排查问题时把 `conftest.py` 里 `stdout=subprocess.DEVNULL` 那两行删掉，
就能直接看到服务端的 traceback ——
平时开着会把 20 个并发请求的访问日志灌满整个测试输出。

# 预判提问与回答

> **与 `GUIDE.md` 第 8 节的分工**：那边是入门八问（为什么用 SQLite、并发怎么保证），
> 适合第一次讲；**本文档是追问向** —— 你说完标准答案之后，评委接着会问的那些。

## A. 关于数据设计

### A1 `remaining`（剩余号）为什么不落库？

不落库，`remaining = total_slots - booked_count` 现算。

**为什么**：一旦落库，它就有了**两个真相来源**。任何一处漏改 `remaining` 都不会报错，
只会让页面上写着"还剩 3 个号"，而实际一个都约不上。
这类 bug 的恶劣之处在于**它不抛异常**——系统说的话和做的事对不上，且没人知道。

**换了会怎样**：如果每秒有几万次查询，`total - booked` 这点算术确实可以忽略，
但真到了那个量级，正确做法也是上缓存（并且明确接受"缓存可能短暂不准"），
而不是把派生值写回数据库、然后假装它和源数据永远一致。

**追问："那 `booked_count` 不也是冗余吗？"**
是，但它是**被事务保护着的唯一写入点**：所有增减都发生在 `BEGIN IMMEDIATE` 事务内，
且总是由"条件 UPDATE"完成。它存在是为了让 `WHERE booked_count < total_slots`
这个判断能在数据库里一次做完——**它换来的并发安全性，大于它带来的冗余风险**。
`remaining` 换不来任何东西，所以不该落库。

### A2 候补队列为什么要单独一张表？在 `appointments` 里加个 `status='waiting'` 不行吗？

不行，因为**它们在语义上是两种不同的东西**：

| | `appointments` | `waitlist` |
|---|---|---|
| 对应现实 | 一张**挂号单** | 一个**排队位** |
| 有没有序号 | 有 `seq_no`，且必须唯一 | 没有，只有名次 |
| 占不占号源 | 占 | 不占 |
| 能不能重复 | 一人只能一张 | 同一人可先排队、再拿号（拿号后自动出队） |

如果塞进一张表：`appointments` 的两个部分唯一索引
`(schedule_id, seq_no)` 和 `(schedule_id, user_id)` 会立刻失效——
候补记录的 `seq_no` 该填什么？填 NULL 的话，唯一索引在 SQLite 里对 NULL 不生效，
于是"一人一张"这条约束**悄悄消失了**。

**换成别的会怎样**：有人会用 `status` 区分 + 加 `WHERE status='booked'` 的部分索引来救。
能work，但每次写查询都要记得带上那个 `WHERE`，
漏一处就是一次静默的数据损坏。**表是最强的约束，比任何"记得加 WHERE"都可靠。**

### A3 递补时为什么不直接给队首，而要"循环取队首 + 重跑规则"？

因为**候补队列是一台延迟求值的规则检查器**。

入队时刻意不校验"同天同科室限 1 号"——那时他确实一个号都没有，校验毫无意义。
但等到有人退号、轮到他时，情况可能已经变了：
**他这中间可能已经约到了同科室的另一个号。**

**只在入队时校验** → 放行后来违规的人；
**只在出队时校验** → 入队时无法给出"你排在第几位"的即时反馈（其实可以，只是意义不同）。

我们的答案是：**入队时只校验"此刻"能判定的，出队时重跑全部。**
不合格者标记 `expired` 顺延给下一位。

**追问：这个机制有什么副作用？**
`expired` 的记录会留在表里。这是刻意的——它与 `cancelled`（用户主动放弃）分开存，
让库里能区分**谁动的手**。对外后果完全一样，都能重新排队。

**顺带堵住的一个漏洞**：队首就是退号者本人时也要顺延。
否则"先排队 → 再退号 → 递补给自己"能把这个号永久锁在手里——
这正是防黄牛要防的霸号行为。

### A4 递补者继承被释放的序号，那为什么代码里还要重跑一遍最小空号算法？

正常路径下两者**必然相等**，重跑看起来是多此一举。

但"必然相等"依赖一个前提：被释放的号确实是当时最小的空号。
如果库里因为任何原因（历史脏数据、手工改库、迁移遗留）出现了不一致，
**直接沿用 `released_seq_no` 会撞上唯一索引 500**，
而重跑算法最多是发一个"看起来不太对但合法"的号。

这是同一个思路的又一次出现：**能让数据库/通用算法决定的，就别信一个推导出来的值。**

## B. 关于并发

### B1 三层防护，去掉一层行不行？

三层挡的是**三种不同的失效**，不是三份保险：

| 层 | 它挡的是 | 去掉它之后 |
|---|---|---|
| 条件 UPDATE | 判断与写入之间的窗口 | 两个请求都读到"还剩 1 个"，都认为自己该拿到 → 超卖 |
| `BEGIN IMMEDIATE` | 读后写被覆盖 | 事务先读后升级写锁，中途被别人插进来 → 读到的是旧值，写回去覆盖对方 |
| 部分唯一索引 | 有人绕过应用层直接改库 | 应用层写得再小心，一条 `sqlite3 data/clinic.db "UPDATE..."` 就能造出两张一样的挂号单 |

**追问："既然有唯一索引，前面两层是不是多余？"**
不是。唯一索引只能告诉你"撞了"，它不知道该怎么处理——
用户拿到的是一条数据库异常，而不是"号已满，已为您排队"。
**前两层负责让正常路径走通，第三层负责让异常路径不越界。**

---

### B2 为什么路由写成同步 `def`？异步框架里这不是反模式吗？

在这个项目里恰恰相反。

`async def` 的路由全在同一个事件循环里执行。同步的 `sqlite3` 调用会**堵住整个循环**，
其他请求连进都进不来——请求之间根本不重叠，SQLite 的写锁**永远不会被竞争**。
那样跑出来的"20 人抢号没有超卖"，证明的不是代码正确，而是**压根没并发起来**。

写成同步 `def`，Starlette 会把它们丢进线程池，请求才真正重叠，锁才会被真的争抢。

**追问："那生产环境呢？"**
生产环境正确的做法是：**要么全异步 + 异步数据库驱动**（asyncpg 那一路），
**要么同步路由 + 线程池 + 连接池**（本项目这一路）。
**最糟的是"async def 里调同步数据库"** —— 那就是纯阻塞，比两条正路都差。

**追问："线程池会不会耗尽？"**
会，所以要设上限。演示规模下（实测 20 并发最慢 26 ms）完全够用；
真上量时这是必须调的参数，而且要和数据库连接池大小一起调。

### B3 `check_same_thread` 那个 bug 是怎么回事？为什么改的是数据库而不是路由？

**现象**：并发下每个请求都 500。
```
sqlite3.ProgrammingError: SQLite objects created in a thread
can only be used in that same thread.
```

**根因**：FastAPI 处理 `yield` 型依赖时会把生成器**扔进一个专门的线程**驱动，
而同步路由函数在**另一个线程池线程**执行——创建连接的线程与使用它的线程必然不同。

**修法**：`connect()` 加 `check_same_thread=False`。
关掉的是一条**与我们的用法不匹配的保守规则**，不是关掉保护本身：
我们的模型是**一个请求一个连接**，生成器一旦 `yield` 就停在原地等，
任意时刻真正在碰这个连接的只有一个线程，只是它不是创建者。

**为什么不改路由**：把路由改成 `async def` 也能绕开（请求不进线程池了），
但代价是全部请求被串行化。为了让一个检查通过而废掉并发能力，本末倒置。

**最关键的一点**：23 条旧测试从没发现它。TestClient 串行处理请求，
anyio 的线程池会**复用同一个 worker 线程**，创建者和使用者碰巧同线程，问题被完美掩盖。
只有并发起来、请求落到不同线程时才暴露。

> 这条是整个项目里最有价值的证据：它证明的不是"我们并发下是对的"，
> 而是"**不并发测，根本发现不了错**"。

---

### B4 唯一索引为什么是"部分"唯一索引（带 `WHERE`）？

因为取消是**软删除**——`cancelled` 的记录仍然留在表里（历史记录加分项要用）。

如果唯一索引不带 WHERE：

```sql
UNIQUE (schedule_id, user_id)
```

那么"张三约了 1 号 → 退掉 → 重新约 1 号"就会被拒绝，
因为库里还留着他那条 `cancelled` 的记录。**退号的人再也约不回来了。**

带上 `WHERE status IN ('booked','pending','completed','no_show')` 之后，
只有"当前有效"的挂号单参与唯一性判断。

**这条索引真正的价值在 R5 暴露出来了**：加了 `pending` 状态之后，
它必须同步进 WHERE 列表——漏掉数据库这一处的话，
应用层照样拦得住，**表面一切正常**，
只有"绕过应用层直接写库"这条路径悄悄失去保护，
而那正是索引存在的唯一理由。

### B5 候补队列的 `position` 为什么不压缩？有人退出后不是会出现空洞吗？

会出现空洞，对外名次是**现算**的（`rank_in_waitlist()`）。

**为什么**：压缩需要一条 UPDATE 同时修改多行
（`UPDATE waitlist SET position = position - 1 WHERE position > X`），
而 SQLite 是**逐行**检查唯一约束的。更新顺序不可控时，
中间状态会撞上 `(schedule_id, position)` 的唯一键。

**换了会怎样**：可以先删掉唯一约束再压缩——但那就等于"为了让一个展示层的操作方便，
拆掉一道数据完整性防线"。**用"展示层多算一次"换"永远不撞键"，这笔交易划算。**

---

### B6 SQLite 的写锁是库级的，会不会成为瓶颈？

会，但**在演示规模下不会**。实测数据：

| 场景 | 结果 |
|---|---|
| 20 并发抢 15 个号 | 最慢 26 ms，15 成功 / 5 排队，记账 40/40 |
| 单接口平均 | 2.7 – 4.4 ms |
| 连续 20 次请求 | 20/20 成功 |

库级锁意味着**所有排班的写操作也要排队**。
真实医院场景里，热门科室放号那一刻确实会有瞬时高峰，
但那是"几百人抢几十个号"的量级——**这点量对 SQLite 来说连热身都算不上**。

**真正的短板不是锁，是"不能水平扩展"**：
库级锁决定了它只能跑单实例，无法靠加机器分担。
这一点在 README 第 8 节主动交代了。

## C. 关于五个加分项

### C1 待确认（`pending`）为什么要占号？不占不是更灵活吗？

不占的话，这 15 分钟里号会被别人直接约走，**"给他留着"就成了句空话**。
我们等于给了一个名义上保留、实际会被抢走的承诺——比不给更糟。

**代价是队列被短暂卡住**，后面排队的人要等。
这个代价是明确的、有界的：卡多久由 `CONFIRM_TIMEOUT_MINUTES` 限定。

> 一句话总结：**宁可牺牲一点流动性，也不给一个兑现不了的承诺。**

**追问："pending 占号，那 `booked_count` 要加吗？"**
要。所以 `pending` 必须进四个地方：
`schema.sql` 两个索引的 WHERE、`db.py` 的迁移、`guards` 的 `ACTIVE_STATUS_CLAUSE`、
以及 `booking` 的最小空号算法。**加起来四处，漏一处就是一处静默的失效。**

---

### C2 超时判定为什么用惰性结算？定时任务不是更自然吗？

三个理由，按重要性排：

1. **后台线程一重启就没了**。演示项目里服务随时会重启，
   而它负责的恰恰是"清理僵尸状态"——**这类最不该丢的东西，放在最容易丢的地方。**
2. **没人来看的时候，超时与否不影响任何人的任何决策。** 早结算晚结算毫无差别。
3. **惰性结算天然幂等**：每次读之前都结算，读到的一定是此刻的真相，不可能"漏掉"。

**什么时候惰性不够用**：如果超时之后需要**主动通知**（短信、推送），
那就必须有定时任务——因为没人来看的时候，通知也得发出去。
本系统没有通知渠道，所以惰性结算完全够用。
**这个边界要说清楚，否则会显得是在逃避定时任务。**

---

### C3 确认接口为什么要拆成两个事务？

因为**那个"失败"不是"操作没做成"，而是"结算的结论就是失败本身"**。

`POST .../confirm` 的执行顺序是：先结算（发现他超时了）→ 再判定能否确认。
如果两者在同一个事务里，抛 `CONFIRM_TIMEOUT` 异常会**把结算一并回滚**：

- 号又变回 `pending`
- 用户看到"确认已超时"
- 刷新一下，发现自己还能确认
- 而那个号已经顺延给别人了

**修法**：路由层拆成两个事务，第一个只做结算并提交。

**同类问题的识别方法**：如果你在一个事务里"先做 A，再根据 A 的结果决定要不要报错"，
就要警惕了——**报错会回滚 A，而 A 的结果恰恰是你报错的依据。**

---

### C4 那些阈值（15 分钟、10 分钟、2 小时、2 次）是怎么定的？

不是精确计算出来的，是**权衡出来的**，每个都能说出上下界：

| 阈值 | 定这个值 | 调小会怎样 | 调大会怎样 |
|---|---|---|---|
| 确认 15 分钟 | 来得及看一眼手机 | 惩罚了守规矩但没及时看通知的人 | 一个号被钉住太久，后面的人干等 |
| 冷却 10 分钟 | 压住反复退抢 | 手抖退错的人没法补救 | 刷号者可以慢慢倒 |
| 取消时限 2 小时 | 给分诊台反应时间 | 患者失去合理的退号权利 | 开诊前 5 分钟退号，空号递补不出去 |
| 爽约 2 次 | 1 次可能是意外 | 误伤偶然失约的人 | 占着不来的成本太低 |

**全部集中在 `app/services/policy.py` 一个文件里**，改一行就生效，
而且没有第二个地方需要同步改。

**为什么这件事值得单独说**：散落各处的魔法数字，
迟早出现"两处都写 15、改了一处"——
**而这类 bug 不会报错，它只是让系统说的话和做的事对不上。**

## D. 关于工程化

### D1 "契约优先"具体怎么做？有什么代价？

**做法**：改表结构先改 `docs/DATA_MODEL.md`，改接口先改 `docs/API.md`，**然后**才动代码。
前后端都按同一份文档写，谁都不许自己猜。

**代价**：写文档的时间是白花的吗？不是。它在本项目里至少避免了三次返工：

1. R2 时定了"对外只有一种错误形状"，前端 `api.js` 因此只写了一**套**错误解析；
2. R4 做前端时，`docs/API.md` 里登记的字段名直接可用，不用去读后端代码；
3. R5 加 `pending` 时，契约先写了"它要占号、要进四个地方"，照着清单改一处划一处。

**它抓到的一次真问题**（很能说明价值）：
R5 新加的七个错误码写进了 `docs/API.md`，
却忘了在 `app/errors.py` 的 `ERROR_HTTP_STATUS` 里登记，
结果全部落到默认分支——**本该 409 的返回了 400**。

> 这说明"契约先行"要**两头都落**：文档写了不算数，代码里那张表才是真正生效的那一处。

---

### D2 号源状态的判定有两份（Python 版和 SQL 版），为什么不合并且只用一份？

这是明知有代价仍做的取舍。

**为什么不能只留一份**：状态不落库，要按状态筛选（`?status=waiting`）
就只能在 SQL 里把判定逻辑再写一遍。**落库能解决它，但引入了两个真相来源，不值当。**

**三道保险**：

1. 两份逻辑放在**同一文件、上下相邻**，改一处必然看见另一处；
2. 判定顺序逐条对齐（停诊 → 有余号 → 有人排队 → 满），分支值用 f-string 引用同一批常量；
3. **显示走 Python（权威），筛选走 SQL（性能）** ——
   SQL 写错只退化成"筛不准"，不会变成"显示错"。

**并且用变异测试证明了这套保险有效**：
故意把 SQL 版漏写"有人排队 → 候补中"那一档（语法完全合法，不报任何错），
一致性检查当场抓出排班 1 被判成 `full` 而非 `waiting`。

---

### D3 FastAPI 的 422 为什么要收编成 400？

因为**前端只需要写一套错误解析**。

FastAPI 对"类型错误"默认返回 422 + `{"detail":[{"loc":["body","schedule_id"],...}]}`，
与业务错误的 `{"ok":false,"error":{"code","message"}}` 是两套结构。
不统一的话，前端每个请求都要写两套分支。

**一个刻意的取舍**：统一时**没有把 `exc.errors()` 的细节塞进 message**。
那会把 `loc=["body","schedule_id"]` 这种内部字段名暴露出去，
前端用不上，反而可能被拿来探测接口结构。

---

### D4 前端为什么不先判断"还有没有号"再决定发不发请求？

因为**判断完到发出请求之间，号可能已经被抢走了**，
前端拿到的是一个过期的结论。

现在的做法是：预约与入候补对前端是**同一个动作**，
点一下，由后端在事务内决定给号还是让排队。

> 这与防超卖是同一套思路：**能让数据库决定的，就不要让应用层猜。**
> 区别只在于，这里的"应用层"是浏览器。

**收益不只是正确性**：前端因此不需要维护"当前号源状态"的本地副本，
也就不会出现"页面显示还有号、点下去说没了"这种尴尬。

---

### D5 XSS 转义做了吗？

做了，而且是**必须做**的：用户姓名是登录时自由填写的，
拼进 HTML 不转义就是**存储型 XSS**——
一个人把姓名写成 `<img src=x onerror=...>`，所有看列表页的人都会中招。

所有拼接都走 `ui.js` 里的 `esc()`，
并且有一条验证：`<img src=x onerror=alert(1)>` 被转成 `&lt;img...&gt;`，
原始标签**未渗漏**。

**追问："还有哪些地方有风险？"**
`innerHTML` 是唯一入口，我们全项目的数据拼接都过 `esc()`；
`href`、`src` 这类属性如果将来要拼接用户输入，
`esc()` 是不够的（需要校验协议，防止 `javascript:`）。
本项目没有 URL 类的用户输入，所以暂时不存在这个问题——**但这是个已知边界。**

### D6 59 条测试怎么组织的？变异测试是什么？

**变异测试**是其中最值得讲的一组。它证明的不是"代码现在是对的"，
而是"**代码要是写错了，这些测试一定会变红**"。
把四个故意改坏的表达式逐个送进去，全部被抓到：

| 故意改坏的地方 | 被抓到的排班数 |
|---|---|
| 漏掉候补分支 | 2 |
| 候补门槛从 `> 0` 改成 `> 1` | 1 |
| 判定顺序颠倒 | 6 |
| 漏掉停诊分支 | 12 |

**这一组自己也踩过一个坑**，值得说：`test_mutation_timeout_really_depends_on_clock`
原来写的是 `clock.advance(policy.CONFIRM_TIMEOUT_MINUTES + 1)`，
而 `policy` 刚被改成十万分钟——于是推进了十万零一分钟，刚好又超过新的截止时刻，

改成 `advance(原阈值 + 1)` 才对。
**"测试参数跟着被测参数一起变"会让变异测试退化成一次毫无意义的重跑。**

## E. 关于扩展

### E1 如果上 MySQL，要改哪些地方？

**核心业务逻辑一行都不用动**——并发正确性靠的是"条件 UPDATE + 事务 + 唯一索引"，
这三样 MySQL 全都有。要改的是下面这些**方言与配置**：

| 位置 | SQLite | MySQL | 为什么 |
|---|---|---|---|
| 驱动 | `sqlite3`（内置） | `PyMySQL` / `mysqlclient` + 连接池 | MySQL 一个请求建一次连接太贵 |
| 事务 | `BEGIN IMMEDIATE` | `SELECT ... FOR UPDATE` 或依赖 InnoDB 行锁 | **见下方重点** |
| **部分唯一索引** | `UNIQUE(...) WHERE status IN (...)` | **MySQL 不支持部分索引** | **最大的坑，见下** |
| 当前时间 | `datetime('now','localtime')` | `NOW()` | 可注入时钟的注入点要跟着改 |
| CHECK 约束 | 建表时生效 | 8.0.16 以下**被静默忽略** | 版本不对的话约束等于没有 |
| `INSERT OR IGNORE` | 支持 | `INSERT IGNORE` | 语义基本一致，注意 `rowcount` 含义 |
| 自增 | `INTEGER PRIMARY KEY` | `AUTO_INCREMENT` | 建表语句 |

#### 最大的坑：MySQL 不支持部分索引

我们的"一人一张有效挂号单"靠的是

```sql
CREATE UNIQUE INDEX ... ON appointments(schedule_id, user_id)
    WHERE status IN ('booked','pending','completed','no_show');
```

MySQL 没有 `WHERE` 子句。解决办法是**利用"唯一索引允许多个 NULL"**：
把状态列拆出一个 `active_mark` 列，有效时填常量（如 `1`），取消/作废时置 `NULL`，
然后建 `UNIQUE(schedule_id, user_id, active_mark)`。
这样已取消的记录（三元组里含 NULL）自动不参与唯一性判断。

> 这个坑值得主动提一句：它说明**"靠数据库约束兜底"这个思路是跨数据库的，
> 但具体怎么兜，每种数据库给的工具不一样。**

#### 事务那一行要重新想

SQLite 是**库级写锁**，`BEGIN IMMEDIATE` 保证同一时刻只有一个写者，天然串行。
MySQL/InnoDB 是**行级锁**，`BEGIN` 之后第一次写才加锁。
好处是不同排班可以并行写（吞吐量上去了），
代价是**可能出现死锁**——比如两个事务按不同顺序锁两行。

应对办法是**固定加锁顺序**（本项目里总是先锁 `schedules` 的那一行，再动 `appointments`），
这在本项目里是自然满足的，因为每次操作都从"取排班"开始。

**结论**：上 MySQL 之后并发能力是**变强**的（库级锁 → 行级锁），
真正要小心的是死锁与部分索引的替代写法。

### E2 用户量上来了怎么办？

分三步，按顺序来，不要跳步：

1. **换 MySQL**（见 E1）——解决单机容量与并发写的问题，改动可控；
2. **读写分离 + 缓存号源状态**——列表页的查询压力最大，
   而号源状态本来就是派生的，缓存它代价最小（接受"短暂不准"即可）；
3. **放号那一刻用队列削峰**——热门科室放号的瞬时高峰，
   与其让几百个请求同时抢数据库锁，不如让它们排队进场。

**本项目没做这三步的任何一步，因为演示规模用不上。**
刻意不做，和没想到，是两回事。

---

### E3 要不要引入 Redis / 消息队列？

**Redis**：如果要加"号源状态缓存"或"分布式锁"，值得引入。
但要注意——**引入 Redis 之后，一致性问题会变成分布式的**：
缓存与数据库的双写一致性、锁的过期时间与业务执行时间的竞态，
每一个都比现在这个"单库 + 事务"的方案复杂一个量级。
**在单机扛得住的时候引入 Redis，是用复杂换性能；在扛不住的时候引入，是用复杂换生存。**

**消息队列**：只在需要**主动通知**时才必须（见 C2）。
短信、推送、微信模板消息都属于这一类——
没人来看的时候，通知也得发出去，惰性结算解决不了。

### E4 真实鉴权应该怎么做？

现在的实现是：**只认 `X-User-Id` 请求头，登录接口是模拟的。**
这意味着**任何人改一下请求头就能冒充他人**，绝不能用于真实场景。
这是题目定位（演示系统）下的取舍，但必须明说，不能含糊过去。

真实系统里至少要有四层：

1. **登录凭证**：手机号验证码（医疗场景最合适，实名且无需记密码）+ 图形验证码防刷；
2. **会话**：服务端签发 JWT，HttpOnly + Secure Cookie 存储，前端 JS 读不到；
3. **接口鉴权**：`X-User-Id` 从 Token 里解出来，而不是客户端传什么信什么；
4. **管理接口独立鉴权 + 操作审计**：本项目 `/api/admin/*` 现在谁都能调，
   真实系统里必须挡在管理端登录之后，且每一次拉黑都要留日志。

**注意**：即使做了鉴权，"防黄牛"那三条规则**一条都不能减**。
鉴权解决"你是谁"，业务规则解决"你能拿几个号"——**这是两件事。**

# 答辩演示脚本

> 目标：**3 分钟讲清一件事 —— 号源不会被两个人同时拿到，而空出来的号会立刻递补给下一个人。**
>
> 本文每条命令都是实测过的，可以直接复制。演示前请务必跑一遍 0.2 的准备动作。

---

## 0. 演示前准备

### 0.1 三条铁律

1. **用脚本起服务**，不要手敲命令：`scripts/serve.bat`（Windows 双击）或 `bash scripts/serve.sh`。
   脚本里的三条硬性要求（隔离环境的 uvicorn 绝对路径、`--host 0.0.0.0`、输出重定向到文件）
   每一条都对应过一次真实的"演示卡死"。
2. **演示前重置数据库**：`python scripts/reset_db.py`。
   上一轮演示留下的排队、退号、拉黑状态，会让你在台上讲不清楚现在的局面。
3. **先自己完整走一遍**。本文第 3 节列了每一步的"翻车点"，照着检查一遍。

### 0.2 健康检查（10 秒）

```bash
python scripts/reset_db.py
bash scripts/serve.sh          # 或双击 serve.bat
```

打开 <http://127.0.0.1:8000/>，确认：

- [ ] 首屏第一条是**「今日 · 口腔科 李建国 · 已停诊」**（排班 7）
- [ ] 科室下拉框里有 **16 个科室**，说明背景数据灌进去了
- [ ] 筛选「口腔科」能看到「候补中」，筛选「心内科」能看到「已满」，两者号源都是 12/12
- [ ] 接口文档 <http://127.0.0.1:8000/docs> 能打开

> **数据扩充后，演示要用筛选定位。** 库里现在是 67 条排班 / 16 个科室，
> 而演示动线集中在排班 1–8。用顶部的科室下拉框选「口腔科」直达排班 1，
> 比在列表里翻要稳——翻的时候很容易点到同科室的其他排班上去。

> 如果页面一直转圈：先看 `server.log` 有没有输出，再确认是不是按脚本启动的。
> 真出现卡死的排查顺序记在 `PROJECT_STATE.md` 决策 21。

## 1. 三分钟主线（浏览器路线）

按这个顺序走，每一步都有明确的"观众应该看到什么"。

### 第 1 步 · 展示局面（30 秒）

打开首页（67 条排班 / 16 个科室 / 20 位医生），指着屏幕说：

> "这是号源列表。四种状态用**颜色 + 符号 + 文字**三重编码：
> ● 可约、■ 已满、▲ 候补中、✕ 已停诊。
> 只靠颜色的话，红绿色盲看到的是四个一样的灰块，黑白打印全部失效。"

然后指向那对排班（科室筛选选「口腔科」看排班 1，再切「心内科」看排班 4）：

> "注意这两条：**号都是 12/12，唯一区别是有没有人排队。**
> 有人排队显示『候补中』，没人排队显示『已满』——
> 这就是『候补』这个机制改变的全部东西。"

### 第 2 步 · 排队（30 秒）

点开排班 1（口腔科 李建国，明天上午，12/12 候补中）→ 用任意身份登录 → 点「加入候补」。

**预期**：显示「候补第 3 位」。

> "现在满员了，所以我自动进了候补队，拿到第 3 位。
> 注意**点一下就行，不需要我判断还有没有号**——
> 判断完到发出请求之间，号可能已经被别人抢走了，
> 前端拿到的是一个过期的结论。**能让数据库决定的，就不要让应用层猜。**"

### 第 3 步 · 退号递补：核心演示（60 秒，本段是重点）

换一个身份登录，进入排班 1 的持号人（或直接进「我的预约」），**退掉一个号**。

**预期**：排队第 1 位的赵六立刻拿到号，但状态不是"待就诊"，而是 **「待确认」**，
下面带一行截止时刻。

> "这里是最关键的一步。
>
> 以前的做法是：有人退号 → 队首直接拿到号。**但那是系统替一个不在场的人做了决定**
> —— 他可能根本不知道自己有个号，于是这个号白空一场，
> 而队列里其他人本来是能来的。
>
> 现在改成了：递补先给一个 15 分钟的**待确认**窗口。
> 这个状态**是占号的**——这 15 分钟里别人抢不走，
> 否则『给他留着』就成了句空话。
> 代价是队列被短暂卡住，而卡多久由阈值明确限定：
> **宁可牺牲一点流动性，也不给一个名义上保留、实际会被抢走的承诺。**"

### 第 4 步 · 确认（30 秒）

以赵六身份登录 → 进「我的预约」→ 点「确认」。

**预期**：状态从「待确认」变成「待就诊」，截止时刻那行消失。

> "确认之后，号才真正归他。
> 这里有个实现细节值得说：后端先结算、再判断能不能确认，
> **这两步必须在两个事务里**。同一个事务的话，
> 一旦判定'已经超时'抛出异常，会把结算**一并回滚**——
> 号又变回待确认，用户刷新一下发现自己还能确认，
> 而那个号已经顺延给别人了。"

### 第 5 步 · 超时顺延（30 秒，可选）

如果时间允许，展示"没确认会怎样"：

```bash
curl -X POST http://127.0.0.1:8000/api/admin/settle
```

> "超时判定是**惰性**的：没有后台线程在轮询，
> 而是每次有人来看之前先结算一次。
> 三个理由：后台线程一重启就没了，而它管的恰恰是最不该丢的僵尸状态；
> 没人看的时候，超时与否不影响任何人的任何决策；
> 惰性结算天然幂等，只要有人来看，状态就一定是对的。"

**注意**：这里的 15 分钟不会真的过去，第 3 节 3.2 讲了怎么在台上演示"超时"。

## 2. 加分项演示（每个 20 秒）

主线讲完后，挑 2–3 个加分项补刀。优先级从高到低：

### 2.1 退号冷却期（推荐，最有说服力）

1. 约排班 2（儿科，25/40 可约）→ 拿到号
2. 立刻退号
3. **立刻再约排班 2** → **409 冷却期内不可预约**

```json
{ "ok": false, "error": { "code": "COOLDOWN_ACTIVE",
  "message": "退号后 10 分钟内不可预约同一排班，请于 15:42 后再试" } }
```

> "冷却期防的不是退号——退号是正当权利。
> 防的是**反复退了抢、抢了退**，把号源当筹码来回倒的刷号行为。"

### 2.2 违规拉黑

```bash
# 拉黑某个用户
curl -X POST http://127.0.0.1:8000/api/admin/users/6/blacklist

# 用该用户身份去约号 → 403
```

```json
{ "ok": false, "error": { "code": "USER_BLACKLISTED", "message": "账号已被限制预约" } }
```

> "爽约累计 2 次自动拉黑。为什么是 2 次不是 1 次：
> 1 次可能是忘了、堵车、临时有事，属于正常波动；
> 连着 2 次说明这个账号的预约已经不具备可信度，
> 而号源是稀缺资源，占着不来等于让别人看不上病。"

### 2.3 取消时限

> "开诊前 2 小时停止自助取消。
> 留给医生与分诊台反应时间：临近开诊时的空号，
> 已经来不及递补给候补者了（他赶不过来），
> 不如让它干脆空着。"

### 2.4 就诊签到

> "就诊当天可以签到，过了当天没签到就记一次爽约。
> 注意爽约的人**确实占了那个号**——
> 只是没来。若把它当成'已释放'，后面的人就能约到同一个号，
> 而这个号在医生那边的叫号单上是有名字的。"

## 3. 翻车点清单（演示前逐条检查）

### 3.1 最常见的翻车：数据库被上一轮演示污染

**症状**：排队人数不对、「候补第 3 位」变成了「候补第 5 位」、
说好的"12/12 候补中"变成了别的数字。

**处理**：`python scripts/reset_db.py`，然后重启服务。
**演示前必做，演示后也做一次**（否则下次打开就是乱的）。

### 3.2 想演示"超时"，但不想等 15 分钟

三种办法，按推荐度排序：

| 办法 | 怎么做 | 适用 |
|---|---|---|
| **改阈值** | 临时把 `app/services/policy.py` 的 `CONFIRM_TIMEOUT_MINUTES` 改成 `0`，重启服务，再调 `/api/admin/settle` | 台上演示，**演示完记得改回来** |
| 只看不演 | 直接调 `/api/admin/settle`，指着返回的计数讲原理 | 时间紧时的偷懒版 |
| 跑测试 | `pytest tests/test_extras.py -k timeout -s`，看测试里时钟拨快后的断言 | 想证明"确实是时钟在起作用"时 |

> 用第二种办法时，返回的计数大概率是 0（还没到时间）。
> 这不丢人，正好可以解释：**"它现在是 0，因为没有到期的记录。
> 结算是幂等的，什么时候跑都不会误伤。"**

### 3.3 演示到一半发现列表里出现了"今天"的过期排班

**正常现象**。今天的排班在过了时段之后仍然会出现在列表里（记录一条都不删），
只是不能预约。这正是"默认隐藏 ≠ 删除"的设计：
过去日期的排班默认不显示，但留了 `only_future=0` 开关可以显式取回。

### 3.4 换身份登录后，按钮状态没变

前端缓存了 `X-User-Id` 在 `localStorage`。
**换个浏览器无痕窗口**或清一下 `localStorage` 最省事。

## 4. 硬核加分：并发演示（如果评委是技术岗）

这一段的杀伤力最大：**它证明的不是"我们并发下是对的"，而是"不并发测，根本发现不了错"。**

### 4.1 跑并发测试（30 秒）

```bash
python -m pytest tests/test_concurrency.py -s
```

实测输出：

```
--- 20 人抢 15 个号 ---
并发请求数     : 20          起跑间隔(最大) : 2.46 ms
拿到号 / 排队  : 15 / 5      序号          : 26..40 连续
排队名次       : [1, 2, 3, 4, 5]
记账 vs 实占   : 40 / 40
```

> "20 个人同时抢 15 个号，结果恰好 15 个人拿到、5 个人排队，
> 序号 26 到 40 连续、没有重复、没有越界，
> **记账的数和实际占号数完全对得上**。"

### 4.2 三个必须解释的点

**① 为什么不用 TestClient？**

> "TestClient 把请求逐个构造、逐个走完，请求之间根本不重叠。
> 用它可以跑出'20 人抢号没有超卖'的漂亮结果，
> 但那证明的不是代码正确，而是**压根没并发起来**。
> 所以我起了真的 uvicorn 进程，用 httpx 走真实 HTTP 打过去。"

**② 光起真进程还不够，起跑线要对齐**

> "线程池是'提交一个立刻跑一个'，
> 很可能第一个都写完提交了、最后一个才刚发出——它们根本没在抢，只是排队。
> 所以我用 `threading.Barrier` 把 20 个请求卡在同一起跑线上，
> 实测最大起跑间隔 2.46 毫秒。"

**③ 为什么路由写成同步 `def` 而不是 `async def`**

> "这是最反直觉的一点。异步框架里按常识该写 `async def`，
> 但那样所有请求会挤在同一个事件循环里串行执行，
> 同步的 sqlite3 调用还会堵住整个循环。
> 那样 SQLite 的写锁**永远不会被竞争**，
> 测出来的'没有超卖'毫无说服力。
> 写成同步 `def`，Starlette 会把它丢进线程池，请求才真正重叠。"

### 4.3 收尾：三层防护

```
第一层  条件 UPDATE   UPDATE ... WHERE booked_count < total_slots AND is_closed = 0
第二层  BEGIN IMMEDIATE   写事务一开始就拿锁，而不是写到一半才升级
第三层  部分唯一索引   (schedule_id, seq_no)、(schedule_id, user_id) 唯一
```

> "三层不是冗余备份，**它们挡的是三种不同的失效**：
> 第一层挡判断与写入之间的窗口，第二层挡读后写被覆盖，
> 第三层挡有人绕过应用层直接改库。"

### 4.4 现场抓到的真 bug（这段最能体现含金量）

> "并发一起，每个请求都 500：`SQLite objects created in a thread can only be used in that same thread`。
>
> 根因是 FastAPI 处理 `yield` 型依赖时会把生成器扔进**一个专门的线程**驱动，
> 而同步路由函数在**另一个线程池线程**执行——创建者和使用者必然不是同一个线程。
>
> 关键问题是：**23 条旧测试为什么从没发现它？**
> 因为 TestClient 串行处理请求，anyio 的线程池会复用同一个 worker 线程，
> 创建者和使用者碰巧同线程，问题被完美掩盖。
> 只有并发起来、请求落到不同线程时才暴露。
>
> 这就是'必须用真 uvicorn 做并发测试'最有力的一条证据。"

## 5. 数据持久化演示（20 秒）

1. 在页面上约一个号，记下它
2. 关掉服务（Ctrl+C）
3. 重新启动
4. 打开「我的预约」，号还在

> "数据存在 `data/clinic.db` 这个单文件里，重启不丢。
> 而且**升级表结构也不会丢**——R5 加了两个字段和一个状态值，
> 走的是迁移而不是重建：建新表、复制数据、删旧表、改名，全程在一个事务里。
> 演示库实测 6 医生 / 8 排班 / 70 用户 / 68 预约 / 2 候补，一条没丢。"

## 6. 收尾三句话

如果时间只剩 30 秒，就讲这三句：

1. **"号源不会被两个人同时拿到"** —— 靠三层防护，其中最后一层是数据库的唯一索引，
   绕过应用层也拦得住。
2. **"空出来的号会立刻递补给下一个人"** —— 靠延迟求值的规则检查，
   入队时不校验、出队时重跑，因为那时情况已经变了。
3. **"这两条在并发下依然成立"** —— 靠真的并发测试，而且**测出来的第一个结果是失败的**，
   是它逼我修好了 `check_same_thread` 那个 bug。
